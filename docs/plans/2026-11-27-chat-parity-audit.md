# Chat parity audit · 27 November 2026

Atum already supports the everyday exchange between a person and an assistant on both devices: replies, edits, reactions, attachments, typing, receipts and moderation. The first investment should be finding an old answer across chats, followed by consistent notification controls and threads in ordinary group conversations. Voice notes are the largest missing composer interaction. For people who choose encryption, the first-device and second-device journeys need to work together. Ordinary chats remain plain by default under the owner's product rule.

## Method and source revisions

This is a static audit of production source on upstream branches. “Has” means a client path for the named task is present. “Partial” means a material room, direction, lifecycle, scope or default-setting restriction. “Missing” means no production entry point was located at this pin. For an absence, the citation points to the nearest relevant dispatch, composer, renderer, settings or membership boundary. A file that mentions an event, a fixture, a generic SDK export or an OS permission alone earns no full credit. Ordinary platform requirements (notification permission, homeserver support, room power level) are assumed. The observations do not establish which store build users have installed or which homeserver settings are deployed.

The maintained public phone client is the audited iOS source. Atum phone here means native iOS. Element X Android provides a second independent reference surface. The scoped desktop AGENTS file is absent at the public desktop pin. The workspace counterpart supplied the architectural guidance.

On desktop the Electron host enables thread support for the human SDK instance. The client-facing Matrix operations live primarily in the SDK renderer. The main process also owns notification delivery, assistant execution and IPC. On iOS the audit followed SwiftUI actions into LiveMatrixSession, SDKTimelineSource, the mapper, native API and notification extension. On the reference clients it compared timeline mappers, composer actions, room-list filters, settings, room membership and the SDK adapters. Negative checks included event names and SDK spellings such as `m.room.tombstone`, successor, knock, poll, beacon, voice, sticker, presence, enable encryption and pin/unpin. ## Gaps by user impact

The order favors frequent person–assistant and small-group work. “Native” means use documented Matrix/SDK contracts with an independently authored Atum interface. “Behaviour reference” means compare what the user can accomplish and implement the interaction in Atum's own design. “Out of scope” gives the recommended product disposition for this audience.

1. **Cross-chat history search — native, both.** Find an assistant's earlier answer without remembering which room it was in. Start with permitted plain rooms and saved results that reopen the exact event. Offer local encrypted indexing only where the device already holds the keys.
2. **Portable notification settings — native, both.** Let a person silence a busy group while still hearing direct mentions. Read the effective homeserver setting, round-trip the change across clients and preserve narrower thread preferences.
3. **Threads in ordinary groups — native, both.** Let people branch a long assistant answer and rejoin the main discussion. Reuse Team Space thread handling; prove assistant replies stay under the intended root and thread reads leave the main timeline marker intact.
4. **Recorded voice notes — native, both.** Add record, review, cancel and send alongside dictation; render playable audio with duration and a file fallback for older clients. Assistant transcription should be an explicit downstream action.
5. **Phone verification — native, mobile.** Someone signing in on a second device should be able to complete, cancel or reject a matching SAS challenge with the other device. Never label a recovered history or a locally matched device ID as a completed peer verification.
6. **Phone-first cross-signing and backup — native, mobile.** A phone-only user choosing private chat needs initial key setup, save confirmation and a fresh-device restore test. Keep the recovery key in the established device custody boundary.
7. **Explicit private people chats — native, both.** Offer encryption at creation with a clear one-way choice. Keep every ordinary default plain. Prove mutual verification and recovery before exposing this choice broadly.
8. **Shared message pins outside Team Space and writable pins on phone — native, both.** Keep a decision or an assistant's instructions visible to everyone. Show who can change the list, and preserve a concurrent pin or removal.
9. **Message forwarding on phone — behaviour reference, mobile.** A person should be able to choose the destination and preview what will leave a conversation. Build on Atum's existing desktop forward semantics and transfer media appropriately across encryption boundaries.
10. **Rich URL cards on phone — native, mobile.** Recognize a document before opening it. Match the desktop policy of homeserver preview for eligible plain rooms and a simple link for encrypted content.
11. **Actionable polls — native, both.** A group decision requires seeing options, voting, and final results. Start with rendering and voting before creating and closing polls; handle disclosed and undisclosed polls.
12. **Static location — native, both.** Let contacts send a place and open it in their system map. Show a readable fallback, request location only on action, and let the sender choose a pin without granting ongoing access.
13. **Room-wide mentions on phone — native, mobile.** Expose an explicit permission-aware choice for authorized senders. Ordinary typed text containing “@room” should stay ordinary text until deliberately addressed.
14. **Room-upgrade continuity — native, both.** A person opening an old conversation should see the replacement and follow it without losing access to earlier history. Validate the successor/predecessor relationship and keep a manual join step when needed.
15. **Unread and favourites list filters — behaviour reference, both.** Add obvious, reversible list controls so pending replies are discoverable without scrolling through assistant and human sections. Preserve Atum's contact grouping and return position.

**Remaining dispositions.** Adopt native sticker rendering before adding pack selection; preserve received images and accessible descriptions. Treat the phone's user-presence indicator as opt-in and distinguish unknown from offline. Defer MatrixRTC as **out of scope for the first chat tranche** because calling requires identity, incoming-call handling, media permissions and an operated RTC transport. Defer live location because background permissions, expiry and stop-sharing are a different commitment from sharing a place. Defer standard Matrix space administration and knocking until arbitrary community rooms enter the product brief. Atum's company membership and invites already have their own authorization model. Defer administrator-initiated upgrades; successor navigation solves the member's immediate problem. Treat desktop simplified Sliding Sync as a performance investigation: measure time to a usable room list, initial bytes and memory at realistic account sizes before changing protocol. These are product choices, not missing homeserver guarantees.

## Open owner decisions and recommended defaults

1. **Which rooms should gain general chat features first?** Start with human groups and opted-in assistant participants. Keep personal assistant DMs simple and expose a thread on demand.
2. **What search scope should users expect?** All accessible personal and company chats, clearly labelled. Search encrypted history locally on the user's device and display index coverage.
3. **When should encryption be offered?** An explicit choice when creating a human DM or group, after verification and recovery pass on both devices. Preserve the plain default and require separate support before admitting an assistant to private rooms.
4. **Which channel governs notification delivery?** The homeserver for portable room modes. Layer Atum's finer thread display and agent activity preferences on top.
5. **How should voice notes reach assistants?** Store a standard voice note. Ask before transmitting audio to a transcription provider unless the user has already enabled that service for the assistant.
6. **Does Atum aim to be a general public Matrix community client?** Prioritize interoperable message handling. Defer public space administration, knock workflows and live location until customer demand changes the scope.
7. **Should calling enter the first parity release?** Defer it. If prioritized later, start with human-to-human calls and a bounded interoperability and operating-cost study.
8. **What may be reused from Element?** Use current clients as behaviour references only. Build against licensed SDKs and preserve Atum's design and existing mobile clean-room process.
